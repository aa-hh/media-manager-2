# Spotting missed searches and stalled torrents (AA-10)

Question: using the Sonarr and Radarr API and rTorrent's status, how can media-manager-2 tell that a search never ran, or that a torrent has stalled or failed? For each failure reason, which recovery actions does their API offer?

Sources are pinned to the latest releases on 2026-10-08: Sonarr `v4.0.20.3014`, Radarr `v6.4.4.10685`, rTorrent `v0.16.25`. All API paths below are the `/api/v3` API, which both apps serve. Line links point at those tags.

## Answer

1. **Sonarr and Radarr never mark a torrent from rTorrent as stalled or failed.** Their rTorrent adapter reads 12 fields per torrent and turns them into one of three states: Completed, Downloading or Paused. It never reads rTorrent's error message, peer counts or tracker status. A torrent with no seeders, or one the tracker refuses, shows as "Downloading" in their queue forever. media-manager-2 has to read rTorrent directly to see these.
2. **Their automatic recovery after a failed download is built for Usenet.** The wiki says failed download handling "is only compatible with SABnzbd and NZBGet by default". In the code, a download only enters the failed path when the download client reports `Failed` or the download is encrypted. The rTorrent adapter never reports `Failed`.
3. **Neither app searches for missing items on a schedule.** Their timed jobs include an RSS sync (reading indexers' feeds of new uploads) but no missing-item search. A search runs on add (if the add asked for one), after a failed download (if enabled), or by hand. If the search on add never fires, nothing retries it.
4. **"A search ran" is visible per item.** Each episode and movie carries `lastSearchTime`. It is set whenever a search asked at least one indexer, whatever the result. A monitored item with no file and `lastSearchTime: null` was never searched.
5. **Recovery in their API comes down to five actions**: start a search command, remove a queue item with `blocklist=true` (which also starts a new search unless `skipRedownload=true`), mark a history item failed, retry an import (manual import or a scan of the download folder), and grab a specific release.

## Supporting detail

### What Sonarr and Radarr read from rTorrent

The rTorrent adapter calls `d.multicall2` for `d.name`, `d.hash`, `d.base_path`, `d.custom1` (label), `d.size_bytes`, `d.left_bytes`, `d.down.rate`, `d.ratio`, `d.is_open`, `d.is_active`, `d.complete` and `d.timestamp.finished` ([S RTorrentProxy.cs L45-59](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Download/Clients/rTorrent/RTorrentProxy.cs#L45-L59)). Status is `Completed` if finished, `Downloading` if active, else `Paused` ([S RTorrent.cs L172-183](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Download/Clients/rTorrent/RTorrent.cs#L172-L183)). Radarr's adapter has the same mapping at the same lines ([R RTorrent.cs L172-183](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/NzbDrone.Core/Download/Clients/rTorrent/RTorrent.cs#L172-L183)).

For comparison, the qBittorrent adapter does map "stalled" and "error" states, but only to `Warning`, with a comment that this is so failed download handling is not triggered ([S QBittorrent.cs L249-284](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Download/Clients/QBittorrent/QBittorrent.cs#L249-L284)). So even on other clients, a stalled torrent never triggers an automatic new search.

### When the failed path runs

`FailedDownloadService.Check` only acts on downloads in state `Downloading` or `ImportBlocked` whose client status is `Failed` or which are encrypted ([S FailedDownloadService.cs L71-92](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Download/FailedDownloadService.cs#L71-L92)). The wiki's Failed Download Handling section says the feature works only with SABnzbd and NZBGet by default ([Servarr wiki source, sonarr/settings.md L861-879](https://github.com/Servarr/Wiki/blob/eae55f91d9cbe1af63df7183184bd128a06c9f83/sonarr/settings.md#L861-L879)).

When a failure is recorded (automatically, by `blocklist=true` on a queue delete, or by `history/failed`), the redownload handler searches again for the episode, the whole season if the failed release covered it, or the movie. It skips this when the user passed `skipRedownload`, when "Redownload Failed" is off, or when the release came from interactive search and "Redownload Failed from Interactive Search" is off ([S RedownloadFailedDownloadService.cs](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Download/RedownloadFailedDownloadService.cs)).

Queue delete flags: `removeFromClient` (default true) deletes the torrent and its data from rTorrent; `blocklist` marks it failed and blocks the release; `changeCategory` moves it to the post-import category instead; all three false means "ignore" ([S QueueController.cs L331-369](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/Sonarr.Api.V3/Queue/QueueController.cs#L331-L369)). `removeFromClient=true` calls `RemoveItem(item, true)`, which deletes downloaded data. On private trackers that risks a hit and run; media-manager-2 may prefer `removeFromClient=false` plus its own rTorrent call.

### Scheduled jobs

Sonarr's timed jobs: refresh monitored downloads, messaging cleanup, update check, scene mapping update, health check, series refresh, housekeeping, recycle bin cleanup, import list sync, backup, RSS sync ([S TaskManager.cs](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Jobs/TaskManager.cs)). Radarr's list is the same idea with movie and collection refresh ([R TaskManager.cs](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/NzbDrone.Core/Jobs/TaskManager.cs)). Neither has a missing-item search. Sonarr also searches after a series refresh through `EpisodeRefreshedService.Search` ([S SeriesScannedHandler.cs](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Tv/SeriesScannedHandler.cs)); which episodes that covers was not checked.

### Lists of missing items

`GET /api/v3/wanted/missing?monitored=true` returns monitored episodes (Sonarr) or movies (Radarr) without a file, each with `lastSearchTime` ([S MissingController.cs L29](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/Sonarr.Api.V3/Wanted/MissingController.cs#L29), [R MissingController.cs L42](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Api.V3/Wanted/MissingController.cs#L42), [S EpisodeResource.cs L24](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/Sonarr.Api.V3/Episodes/EpisodeResource.cs#L24), [R MovieResource.cs L86](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Api.V3/Movies/MovieResource.cs#L86)). Radarr's list may also include movies not yet released; filtering by availability was not checked.

## Unconfirmed

- Whatbox's rTorrent version. The commands above exist in 0.16.25; `t.*` scrape counters and `d.message` have been in rTorrent for years, but they were not checked against Whatbox's build.
- The exact text private trackers send for an unregistered or deleted torrent. It varies by site.
- Whether Whatbox runs Sonarr v4 and Radarr v6. Older Radarr releases may lack `lastSearchTime` on movies; it arrived with Radarr's database migration 234 ([R migration](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/NzbDrone.Core/Datastore/Migration/234_movie_last_searched_time.cs)).
- Sonarr and Radarr's own hosted API reference (sonarr.tv/docs/api, radarr.video/docs/api) was not read line by line; endpoints were confirmed in source instead.
