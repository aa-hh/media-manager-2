## Goal

Give the owner one place to see what automation gave up on (Flagged / Needs you, with Missing and Below cutoff filters), one merged event log (History, with Mark as failed) and its Blocklist (with Unblock + Undo), and a Health screen that merges Sonarr's, Radarr's and media-manager-2's checks behind a top-bar badge. All of it presents data the live-downloads and automatic-fixes work already records (`problems`, `problem_steps`, `tracker_cooldowns`, `torrent_issues`, `torrent_grabs`, `arr_queue`, `search_log`, `dependency_status`) plus Sonarr/Radarr's own history, blocklist, wanted, health and diskspace endpoints. Nothing leaves the app (no push/email, no snooze).

## Decisions taken (owner may override later; executors do not)

1. **Routing**: path-based, no router library. `/` Downloads (today's behaviour), `/flagged`, `/history`, `/blocklist`, `/health`. `history.pushState` + `popstate`. The server already serves `index.html` for any extensionless path (`src/server/app.ts:370-376`).
2. **Nav**: a `Nav` component in the Home header, after the search box: Downloads · Flagged N · History · Health [badge]. Blocklist is reached from a link in the History header, not nav. Library/Calendar items belong to AA-30 and are not added here.
3. **Route mounting**: every new server module exports `createXRoutes(...)` (a Hono) and is mounted in `src/server/api.ts` under one new optional `ApiActions` field each, one `if (actions?.x !== undefined) api.route('/x', createXRoutes(actions.x))` line each; wired in `src/server/index.ts` inside the existing `createApiRoutes(database, {...})` call. No new `CreateAppOptions`.
4. **Health refresh**: a `health-check` job every 5 min plus `POST /api/health/check` ("Run all checks"). Snapshot lives in memory (no table). Client polls `GET /api/health` every 60 s for the badge; no extra SSE stream.
5. **Worst problem / badge**: levels `ok < notice < warning < error`. Risk = `error`. Badge text: `${n} RISK(S)` when errors > 0, else `${n} WARNING(S)` when warnings > 0, else no badge (quiet when healthy). Notices never badge.
6. **Tracker account stats** (global ratio, hit-and-run count vs limit, count-increase warnings, Blutopia lifetime-vs-active distinction) depend on AA-39, which is not built. Health's tracker table shows per host: reachability (no `tracker_down` issue), cooldown (from `tracker_cooldowns`, exact refusal text, known/unknown), and `account: { kind: 'not_set_up' }` rendered as "Account stats are not set up yet". The shape leaves room for AA-39 to fill `{ kind: 'ok', ratio, ratioMinimum, hitAndRun, hitAndRunLimit }` later. Known refusal texts already live in settings (`trackerConfiguration.refusalTexts`, `src/server/trackers.ts:60-64`); nothing new there.
7. **R2 backup age** depends on AA-42. Contract: AA-42 adds table `backup_runs` (id, started_at, finished_at ms epoch, outcome 'ok'|'failed'|'skipped', detail, object_key, bytes, sha256). Health reads the age as `SELECT MAX(finished_at) FROM backup_runs WHERE outcome = 'ok'`, after checking `sqlite_master` that the table exists. Table absent, or no ok row → `{ kind: 'not_set_up' }` ("Cloudflare R2 backups are not set up yet", notice); older than 26 h → warning (`stale`); else ok. This epic adds no `backup_runs` migration and imports nothing from `src/server/backup.ts`.
8. **Jobs ran on time**: `createJobRunner` gains per-job `lastStartedAt`, `lastFinishedAt`, `lastFailed` and a `status()` method; a job is late when it has not finished within `3 × intervalMs` of now (measured from runner start when it never ran).
9. **Disk warning threshold**: free < 25 GB or < 10 % of total → warning. Drives come from both services' `/api/v3/diskspace`, deduplicated by `path`.
10. **Mark as failed**: client confirmation panel, then `POST /api/history/:service/:id/failed`. Server: (a) `GET /api/v3/downloadclient`; if any client has `enable === true && removeFailedDownloads === true` → 409 `remove_failed_on` (the only way to keep the seeding torrent safe: that flag makes the service remove the torrent). (b) `POST /api/v3/history/failed/{id}`. (c) `GET /api/v3/config/downloadclient`; if `autoRedownloadFailed === true` the service searches itself; else if the subject is a manual download (`protection.isProtected`) no search; else send `EpisodeSearch`/`MoviesSearch` exactly as `src/server/searches.ts:100-102`. Library file is never touched (the services' mark-failed does not delete library files; the test asserts no `episodefile`/`moviefile` DELETE is sent). The design frame `fs0ud` says "deletes the file"; the epic text wins: preserve the file. The "Remove the torrent from rTorrent instead…" option in `fs0ud` is dropped (epic: preserve the seeding torrent).
11. **"By whom" on the blocklist**: new table `blocklist_marks` written only by this epic's routes (mark-failed, and the existing `/api/queue/:service/:id/remove` route when `release` is `blocklist` or `blocklist_search`). Attribution order: mark present → "by you from the title's history" / "by you from Live downloads"; else `torrent_grabs.release_title` match → problem with that hash whose kind is one of `stalled`, `unregistered`, `damaged`, `tracker_down`, `import_bad_release` → "by media-manager-2: {problem.summary}"; else "by Sonarr/Radarr: {message}". `stalls.ts`/`imports.ts` are not edited.
12. **Undo after Unblock**: client-side only. The row leaves the list and a line "Unblocked {title}. {Service} can grab that release again on the next search. Undo" shows for 8 s; the `DELETE /api/blocklist/:service/:id` is sent only when the 8 s pass without Undo. (The services have no "add to blocklist" API, so a server-side undo is impossible.)
13. **History event filters** map by `eventType` *name* after fetching (no `eventType` ints in the query): Grabs=`grabbed`; Imports=`downloadFolderImported`,`seriesFolderImported`,`movieFolderImported`; Failures=`downloadFailed`,`downloadIgnored`; Deletions=`episodeFileDeleted`,`movieFileDeleted`; Automatic fixes = media-manager-2 problem steps. `episodeFileRenamed`/`movieFileRenamed` appear under All only.
14. **Missing/cutoff "last result"**: `never searched` | `in queue` | `grabbed {releaseTitle}` (a `torrent_grabs` row for the subject with `grabbed_at >= lastSearchAt`) | `nothing grabbed`. Next search time = `searchDueAt(...)` from `src/server/searches.ts:24-28`; movies' `availableAt` reads `availability_seen` by the key format at `searches.ts:39` (`${service}:${type}:${id}`), null when absent. No new schedule is introduced.
15. **Labels for subjects** (titles for problems that only carry ids): new `src/server/labels.ts` with an in-process cache; movie → `GET /api/v3/movie/{id}` → `"{title} ({year})"`; episode → `GET /api/v3/episode/{id}` → `"{series.title} SxxEyy"`; failure → `"Radarr movie 7"` / `"Sonarr episode 31"`. Torrent subjects go through `findGrab` first, falling back to the torrent name.
16. **Dismiss** on Flagged rows (design critique P2) is not built: the problems model has no dismissed state and the epic does not ask for it.
17. **Pick a release from Flagged** reuses `PickRelease` (`src/client/PickRelease.tsx:243-250`). For Sonarr targets the wrapper first fetches `/api/owned/series/{seriesId}/episodes` (`src/server/owned.ts:76`) for the `episodes` prop; for Radarr `/api/owned/movie/{movieId}` (`owned.ts:82`) for `movieHasFile`.
